## 2. Карта риска (что проверено в коде и признано корректным)

Чтобы аудит не выглядел списком только проблем — явно подтверждённые вещи:

* **Контракты EF Core**: `SaveChangesInterceptor` (sync + async + `SaveChangesFailed*`),
  `DbCommandInterceptor` (Reader/Scalar/NonQuery, sync + async), `IDbTransactionInterceptor`,
  `IIdentityResolutionInterceptor`, `IMaterializationInterceptor` — сигнатуры совпадают; отмеченные
  в коде места, где `Task` обязателен вместо `ValueTask` (`TransactionCommittedAsync`), действительно
  реализованы через `Task`.
* **Порядок интерсепторов**: `EfInterceptorsSetup.BuildInto` и `UseEfInterceptorsFrom` сортируют по
  `IOrderedInterceptor.Order`; `OrderBy` в LINQ стабилен, поэтому «ничьи» (`-300` validation/custom
  validation, `-200` guards) сохраняют порядок регистрации. Шифрование (75) идёт до ChangeLog (100) —
  как и заявлено в CHANGELOG (S-5).
* **Multi-tenancy**: `TenantId` неизменяем (`Original != Current` → `CrossTenantAccessException`),
  вставка без текущего тенанта запрещена, кросс-тенантная модификация/удаление запрещены,
  tenant-id подмешивается в ключ L2-кэша (`TenantKeyContributor`) автоматически.
* **Шифрование**: AES-256-GCM, случайный nonce 12 байт, tag 16 байт, версионированный payload
  `[ver][nonce][tag][cipher]`, `AssociatedData` (AAD) с fail-closed поведением, legacy-формат только
  в `Lenient`, `Strict` отвергает; ключ затирается в `Dispose`; `IsEncrypted` не бросает.
* **Outbox-процессор**: claim через уникальный `Guid`-токен (без гонок «одинаковый timestamp»),
  dead-letter после `maxAttempts`/`PermanentOutboxException`, экспоненциальный backoff с джиттером,
  адаптивный polling, метрики с низкой кардинальностью тегов.
* **Cache-инвалидация**: снимок `ChangeTracker` один раз на `SaveChanges` (защита от O(n²)-сканов),
  отложенная инвалидация до коммита транзакции, откат — без инвалидации, single-flight (sync через
  `SemaphoreSlim`, async через `Lazy<Task>`), лимиты по строкам/байтам с bypass вместо OOM.
* **Регистрация**: `AddEfInterceptors` + `UseEfInterceptorsFrom`, `TenantModelCacheKeyFactory`
  подключается автоматически, предупреждения о «command-интерсептор на нереляционном провайдере» и
  «L2-кэш + session-init» пишутся в лог.
* Никаких `async void`, `DateTime.Now`, `lock(this)`, хранения секретов в исходниках не найдено.

## 3. Находки

### P1-1. Генератор контрактов не попадает в NuGet-пакет (фича не работает у потребителей)

`src/EfCore.Interceptors/EfCore.Interceptors.csproj:49-52` пакует только `README.md` и
`EfCore.Interceptors.Analyzers.dll`:

```xml
<None Include="..\EfCore.Interceptors.Analyzers\bin\$(Configuration)\netstandard2.0\EfCore.Interceptors.Analyzers.dll"
      Pack="true" PackagePath="analyzers/dotnet/cs" ... />
```

`EfCore.Interceptors.Generators.dll` (source generator для `[Auditable]`, `[SoftDeletable]`,
`[HasDomainEvents]`) в пакет **не включён**, хотя в самой библиотеке он подключён как анализатор
(`ProjectReference ... OutputItemType="Analyzer"`). Следствие: у потребителя NuGet-пакета
частичные классы с этими атрибутами **не получат сгенерированных членов** → ошибки компиляции
`IAuditableEntity` не реализован, `DomainEvents` не объявлен и т.п. В репозитории это не проявляется,
потому что в тестовом проекте генератор подключён напрямую.

**Проверить:** `dotnet pack -c Release` → распаковать `.nupkg` → `analyzers/dotnet/cs` должен содержать
**две** dll.
**Исправление:** добавить `None Include="..\EfCore.Interceptors.Generators\bin\$(Configuration)\netstandard2.0\EfCore.Interceptors.Generators.dll" Pack="true" PackagePath="analyzers/dotnet/cs"` + smoke-тест «пакет в отдельном проекте».

### P2-1. ✅ ИСПРАВЛЕНО. Парсер таблиц L2-кэша возвращал имя схемы вместо имени таблицы

`Commands/CachingCommandInterceptor.cs` (regex `ReadTablesRegex` / `WriteTablesRegex`) для
`FROM "public"."Orders"` записывал зависимостью `public`, а не `Orders`: альтернатива
`"..."` (одна кавычённая часть) срабатывала первой. Для PostgreSQL/схем (`"dbo"."Orders"` и т.п.)
таргетная инвалидация (`InvalidateTable`, поколения таблиц, `Generation`) вырождалась в «сбросить всё
в этой схеме», т.е. заявленная фича 06.4 фактически не работала. Проверено симуляцией regex до/после:
`SELECT ... FROM "public"."Orders"` → было `{public}`, стало `{Orders}`. Регрессионные тесты — §5.

### P2-2. ✅ ИСПРАВЛЕНО. Дашборд: dead-letter не виден за свежими pending-строками

`src/EfCore.Interceptors.Dashboard/DashboardStore.cs:39-54` — `Take(take)` применялся **до**
фильтра по статусу, поэтому `GET /api/outbox?status=Dead` возвращал пустой список, пока существует
≥ N более новых pending-сообщений: «отравленные» сообщения становились невидимыми в UI (retry
недоступен). Класс помечен «client-side over keyset pages», но порядок операций был неверным.
Исправлено: фильтр статуса в SQL до `Take`.

### P2-3. Снимок ChangeTracker не сбрасывается, если интерсептор бросил исключение

`Saving/ChangeTrackerSnapshot.cs:13-45` кэширует `ChangeTracker.Entries()` в
`ConditionalWeakTable<DbContext, List<EntityEntry>>` и чистит его только в `SavedChanges`/`SaveChangesFailed`.
Но `SoftDeleteSaveChangesInterceptor.SavingChanges` (`Saving/SoftDeleteSaveChangesInterceptor.cs:26-37`)
вызывает `ConvertDeletes` **без** `try/catch → End`, в отличие от `AuditSaveChangesInterceptor`
(`:34-52`, где защита есть). `SoftDeleteCascadeException`, `EntityValidationException`
(`ValidationSaveChangesInterceptor`), исключения guard-интерсепторов летят наружу, и снимок остаётся
в кэше.

Последствия:
1. Следующий `SaveChanges` в том же контексте работает по **устаревшему списку `EntityEntry`** —
   сущности, добавленные в трекер после исключения, не попадут в аудит/tenant/outbox/soft-delete.
2. `AsyncLocal<HashSet<DbContext>> _active` (`:15`) продолжает держать ссылку на контекст до конца
   async-flow — удержание памяти в request-scoped сценариях.

**Рекомендация:** обернуть мутации в `try/finally`/`catch` во всех «пишущих» интерсепторах
(`SoftDelete`, `Validation`, `CustomValidation`, `MassOperationGuard`, `EntityGuards`, `RowLevelSecurity`)
по образцу `Audit`, либо централизовать: `ChangeTrackerSnapshot.Begin(context)` в первом
`SavingChanges` и `End` в `SaveChangesFailed` + «поколение» снимка (номер цикла сохранения), чтобы
забытый `End` не влиял на следующий вызов.

### P2-4. `UseProductionDefaults()` несовместим с рекомендованными `BulkExtensions.*`

`EfInterceptorsSetup.UseProductionDefaults` (см. `EfInterceptorsSetup.cs:130-141`) включает
`WithStrictQueryPolicy(forbidExecuteDelete: true, forbidExecuteUpdate: true)`, а
`Queries/StrictQueryPolicyQueryExpressionInterceptor.Check` бросает `QueryPolicyViolationException`
по имени метода `ExecuteDelete*`/`ExecuteUpdate*`. При этом «безопасные» хелперы
`BulkExtensions.ExecuteSoftDeleteAsync / ExecuteAuditedUpdateAsync / ExecuteEncryptedUpdateAsync`
(`BulkExtensions.cs:19-120`) реализованы именно через `ExecuteUpdateAsync`. Итог: включив
production-дефолты, потребитель получает исключение на каждом bulk-хелпере, который библиотека сама
и рекомендует.

**Рекомендация:** либо пропускать `ExecuteUpdate/ExecuteDelete`, пришедшие из `BulkExtensions`
(например, через `TagWith("efi:bulk-safe")` и allow-list в политике), либо включать
`forbidExecuteUpdate/Delete` только вместе с предупреждением в документации и примером.

### P2-5. `AllowUnsafeBulkOperations()` молча сбрасывает политику raw-SQL

`EfInterceptorsSetup.Commands.cs:169-181`: метод удаляет **все** `StrictQueryPolicyQueryExpressionInterceptor`
и создаёт новый с дефолтами (`forbidIgnoreQueryFilters: true`, `forbidExecuteDelete/Update: false`).
Если до этого была настроена `WithStrictQueryPolicy(forbidUntaggedRawSql: true, rawSqlBypassTag: "...")`,
эта защита (S-2) тихо исчезает. Ожидание пользователя — «снять только bulk-запрет».
**Рекомендация:** запоминать последние настройки политики в `EfInterceptorsSetup` и пересоздавать её
с сохранением `forbidUntaggedRawSql` / `rawSqlBypassTag`.

### P2-6. Outbox читается «в память целиком» в health-check и статистике дашборда

* `HealthChecks/EfInterceptorsHealth.cs:44-52` — `Where(m => m.ProcessedAtUtc == null).Select(...).ToListAsync()`
  тянет **все** необработанные строки, чтобы посчитать количество и лаг. На outbox в сотни тысяч строк
  health-проба сама становится источником деградации (и это ровно тот случай, который проба должна
  детектировать).
* `Dashboard/DashboardStore.cs:22-36` (`GetOutboxStatsAsync`) — то же самое.

Причина честная (сравнения `DateTimeOffset` не транслируются на SQLite), но решение можно сделать
дешёвым: `Count()` + keyset-страница до первой «свежей» строки (или `Min` по колонке в тиках/`long`).
**Рекомендация:** ограничить окно (`Take(страница)` в цикле с ранним выходом), добавить тест на 10k строк.

## 7. Приложение: как воспроизвести проверки аудита

* Синтаксический разбор: `pip install tree_sitter tree_sitter_c_sharp`, обход всех `*.cs`,
  подсчёт узлов `ERROR`/`is_missing`.
* Инвентаризация API: regex по `EfInterceptorsSetup*.cs` (`public EfInterceptorsSetup With\w+`) и
  сверка с `README*.md`, `samples/**`, `tests/**`.
* Regex-парсеры таблиц: извлечь литерал `TableReference` из исходника, декодировать verbatim-строку
  (`""` → `"`), скомпилировать `ReadTablesRegex`/`WriteTablesRegex` и прогнать набор SQL-примеров
  (PostgreSQL `"schema"."Table"`, SQL Server `[dbo].[Table]`, MySQL `` `db`.`Table` ``, bare, JOIN,
  подзапрос, `UPDATE OR IGNORE`).
