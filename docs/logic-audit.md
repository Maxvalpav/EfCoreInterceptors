# Аудит логических ошибок — EfCoreInterceptors

Проверяемые сценарии и найденные/вероятные логические дефекты.
Формулировки — гипотезы по документированному поведению; каждую стоит
закрыть регрессионным тестом.

## 1. Audit + SoftDelete

**Дефект:** при soft delete сущность переводится в `Modified`. Если
`AuditSaveChangesInterceptor` выполняется **до** soft delete, то `UpdatedAtUtc`
не будет проставлен (на момент аудита состояние было `Deleted`).
Если после — будет. Порядок не зафиксирован → недетерминированный результат.

**Тест:** `Remove(entity); SaveChanges();` → ожидаем `IsDeleted == true`
**и** `UpdatedBy == currentUser`.

## 2. Audit: защита Created* полей

`IsModified = false` для `CreatedAtUtc/CreatedBy` — верно, но:
- при `State == Added` для сущности, пришедшей с уже заполненным `CreatedBy`
  (импорт/миграция), значение молча перезатирается;
- в TPT/owned-типах свойство может лежать в другой таблице — обращение
  `entry.Property("CreatedBy")` бросит `InvalidOperationException`, если
  свойство не замаплено. Нужна проверка `entry.Metadata.FindProperty(...) != null`.

## 3. DomainEvents: снапшот до сохранения

Логическая дыра: события снимаются **до** `SaveChanges`. Если хендлер,
вызванный после коммита, сам добавляет события — они уже не будут
диспетчеризованы в этом цикле (по крайней мере не гарантированно).
Также: если во время `SaveChanges` EF-генерируемые ключи ещё не назначены на
момент снапшота, событие может нести `Id == 0`. Событие нужно
проецировать **после** сохранения, а снимать — только ссылки.

## 4. DomainEvents при откате

README: «при неудачном сохранении события остаются на агрегатах». Но если
`SaveChangesFailed` не вызывается (например, исключение в самом интерсепторе
или отмена по токену), буфер не восстановится → **потеря событий**.
Нужно покрыть `SaveChangesCanceled`/`SaveChangesFailedAsync`.

## 5. ChangeLog: PK у Added-сущностей

Для `Added` с базой-генерируемым ключом PK на момент `SavingChanges`
неизвестен → в лог попадёт `0`/`null`. Корректно: записывать ChangeLog в
`SavedChanges` (после назначения ключей) либо во второй `SaveChanges`
внутри той же транзакции.

## 6. ChangeLog и shadow/owned properties

Дифф «по изменённым свойствам» обычно обходит `entry.Properties`, что не
включает owned-навигации и коллекции. Изменение owned value-object не
попадёт в аудит-трейл — молчаливая потеря аудита (комплаенс-риск).

## 7. SoftDelete и каскады

`Remove(parent)` при `DeleteBehavior.Cascade` помечает детей `Deleted`.
Если дети не `ISoftDeletableEntity` — они удалятся физически, а родитель
останется. Получим **осиротевшую** запись с `IsDeleted = true` и
пропавшими детьми. Нужна политика: запрет, каскадный soft-delete, или
явная ошибка.

Обратный случай: `Remove` у soft-deletable ребёнка при required-связи —
EF может считать связь «severed» и всё равно попытаться занулить FK.

## 8. Повторное удаление

`Remove` уже удалённой (IsDeleted=true) сущности снова проставит
`DeletedAtUtc` — «перезапись» даты удаления. Нужна идемпотентность:
если `IsDeleted` уже true — не менять `DeletedAtUtc`.

## 9. MultiTenancy: сравнение и null

- `TenantId` объявлен `string?`. Сущность, вставленная при
  `CurrentTenantId == null`, станет «общей» и будет видна… никому
  (фильтр `TenantId == null` совпадёт только у null-тенанта). Нужен
  явный запрет вставки без тенанта.
- Сравнение строк тенанта чувствительно к регистру в C#, но может быть
  нечувствительно в БД (collation) → guard пропустит/заблокирует не то.

## 10. Кэш второго уровня

- **Ключ по тексту SQL + параметры** игнорирует `CommandTimeout`,
  `IsolationLevel` и, главное, **query filters, зависящие от тенанта/юзера**,
  если те попадают в SQL как константы — тогда ок, но если как параметры —
  ключ должен включать их значения. Проверить, что параметры входят в ключ
  **включая** `DbNull` и типы (иначе `'1'` и `1` схлопнутся).
- «Внутри транзакции кэш отключён» — но записи в транзакции при
  `invalidateOnWrites` инвалидируют кэш **сразу**, а не после коммита.
  Откат транзакции → кэш уже сброшен (безопасно), но параллельный поток мог
  успеть закэшировать **грязные** данные, если чтение шло из той же
  транзакции. Инвалидировать нужно на `TransactionCommitted`.
- Кэширование `DbDataReader` требует полной буферизации; если возвращается
  «ленивый» reader, второй потребитель получит уже вычитанный поток
  (`InvalidOperationException` / пустой результат).

## 11. N+1 детектор

Считает повторы шаблона SQL в рамках контекста. Ложные срабатывания:
пакетная обработка (цикл по 1000 сущностям — это осознанный дизайн),
`DbContext` с длинным сроком жизни (Blazor Server) → детектор «зашумит»
и его выключат. Нужен сброс счётчика по времени/по scope.

## 12. ConcurrencyRetry

- **ClientWins** делает last-write-wins, затирая чужие изменения — это
  корректно только для явно выбранных сущностей, а не глобально.
- **StoreWins** «перезагрузка» + повтор `SaveChanges` может зациклиться
  на удалённой в БД строке (`entry.GetDatabaseValues() == null`) — нужно
  отдельно обработать «строка удалена».
- Retry внутри интерсептора **не может** повторить внешнюю транзакцию: если
  вызывающий код открыл `BeginTransaction`, повтор пройдёт в уже
  сломанной/абортированной транзакции. Retry должен отключаться при
  `context.Database.CurrentTransaction != null`.

## 13. MassOperationGuard

Порог считает `ChangeTracker.Entries()`. Легитимный сид/импорт упадёт.
Кроме того, ExecuteUpdate/ExecuteDelete (bulk) вообще не проходят через
`SaveChanges` → guard их не увидит, хотя они опаснее всего.

## 14. VersionIncrement + ConcurrencyRetry

При StoreWins-перезагрузке версия перечитывается из БД, затем интерсептор
инкремента может отработать ещё раз → +2 к версии и рассинхрон с реальным
числом изменений.

## 15. WritesRequireTransaction

`SaveChanges` без явной транзакции EF всё равно оборачивает в неявную
транзакцию **только если команд > 1**. Одиночный INSERT пойдёт без
транзакции → интерсептор бросит `MissingTransactionException` на совершенно
нормальном коде. Нужно исключать `CommandSource.SaveChanges`.

## 16. IdentityResolution: NewestWins

Сравнение по `UpdatedAtUtc` падает/ведёт себя неверно, если:
- у одного из экземпляров `UpdatedAtUtc == default` (новая сущность) —
  «новая» проиграет старой;
- разные часовые пояса / `DateTime.Now` вместо UTC;
- равные штампы (в пределах разрешения таймера) — поведение не определено.

## 17. Метрики

`ef.command.duration` без тега `success/failure` и без нормализованного
`db.operation` даст высокую кардинальность, если в теги попадает текст SQL.
Проверить, что SQL не используется как tag value.

## 18. Sampling логов

`WithSqlLogging(sampleRate: 0.25)` — если сэмплирование сделано через
`Random.Shared`, то это ок; если через `new Random()` в поле без
синхронизации — гонка и неравномерное распределение.

## 19. LongRunningTransactionDetector

Watchdog по таймеру должен снимать регистрацию транзакции в
`TransactionFailed`/`RolledBack`/`Disposed`, иначе — вечные предупреждения
и утечка записей о транзакциях.

## 20. ConnectionLifecycleLogging: маскирование

Маскирование `Password/Pwd/Secret/Token` по подстроке не покроет
`User ID=...;Password='a;b'` (экранированные разделители) и провайдер-
специфичные ключи (`AccountKey`, `Api Key`, `Authentication`).
Лучше: `DbConnectionStringBuilder` + whitelist ключей.
