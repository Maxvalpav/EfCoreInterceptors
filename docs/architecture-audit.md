# Аудит архитектуры — Maxvalpav/EfCoreInterceptors

Дата: 2026. Объект: библиотека `EfCore.Interceptors` (EF Core 10 / .NET 10).

## 1. Общая оценка

Проект структурирован разумно: разделение по типам интерсепторов
(`Saving/`, `Commands/`, `Connections/`, `Transactions/`, `Queries/`,
`Materialization/`, `Tracking/`, `Observability/`), отдельные `Abstractions/`
и `Entities/`, отдельный пакет интеграции с MediatR, samples, benchmarks, CI.
Это правильная «библиотечная» топология.

Основная архитектурная проблема — **широта**: ~60 интерсепторов в одном
NuGet-пакете. Это монолит по назначению (аудит, кэш, шифрование, outbox,
метрики, governance), у которого нет единого домена ответственности.

## 2. Ключевые замечания

### 2.1 Один пакет — много ответственностей (SRP на уровне пакета)
Шифрование (AES-GCM), кэш второго уровня, outbox, метрики и валидация —
это разные жизненные циклы, разные зависимости и разные риски безопасности.
**Рекомендация:** разбить на `.Core`, `.Auditing`, `.Outbox`, `.Caching`,
`.Security`, `.Observability`. Иначе любое CVE в криптоблоке заставляет
обновлять всех потребителей.

### 2.2 Кэш второго уровня на уровне `IDbCommandInterceptor`
Кэширование по строке SQL + параметрам — архитектурно хрупко:
- нет учёта схемы/таблиц, участвующих в запросе (инвалидация «по имени
  таблицы» вручную — источник рассинхрона);
- кэш живёт на процесс, что ломается при масштабировании (несколько инстансов
  отдают разные данные);
- материализованные сущности могут попадать в трекер разных контекстов.

**Рекомендация:** явно пометить как «dev/single-instance», либо ввести
абстракцию `ICacheStore` с реализацией на Redis и автоматическую
инвалидацию по `IEntityType` из `CommandSource`/тегов.

### 2.3 Состояние, ключуемое по экземпляру `DbContext`
Домен-события/outbox буферизуются в интерсепторе, а интерсептор может быть
синглтоном на несколько контекстов. Словарь `DbContext -> state` без
`ConditionalWeakTable` и без гарантированной очистки при исключении =
**утечка памяти**. Проверить: очистка в `SaveChangesFailed`,
`SaveChangesCanceled`, и при `Dispose` контекста (события контекста нет —
нужен `ConditionalWeakTable`).

### 2.4 Порядок интерсепторов не специфицирован
`WithSoftDeletes` + `WithAudit` + `WithChangeLog` + `WithOutbox` критически
зависят от порядка: ChangeLog должен видеть уже проставленные
`UpdatedBy/UpdatedAtUtc`, а soft-delete должен отработать **до** ChangeLog,
иначе действие запишется как `Deleted`, хотя физически это `Modified`.
EF вызывает интерсепторы в порядке регистрации, но fluent-API этого не
документирует и не навязывает.
**Рекомендация:** ввести приоритеты (`Order`) и сортировку в
`EfInterceptorsSetup.Build()`.

### 2.5 Модификация текста SQL (QueryHints)
`CommandText += hint` — провайдер-зависимая операция, ломающая план и
несовместимая с батчингом EF (в одной команде несколько statement'ов).
Хинт, добавленный в конец батча, применится не к тому запросу.
**Рекомендация:** применять только к командам с одним statement и явно
проверять `CommandSource`.

### 2.6 ReadOnlyGuard / RawSqlUsageDetector — эвристики по тексту
Регекс/поиск подстрок по SQL даёт как ложные срабатывания (слово DELETE в
комментарии — README это признаёт), так и пропуски (`WITH x AS (...) INSERT`,
хранимые процедуры, `MERGE`, `sp_executesql`). Для guard'а безопасности
эвристика неприемлема.
**Рекомендация:** опираться на `CommandEventData.CommandSource` и на
`ChangeTracker`, а текстовую проверку оставить дополнительным слоем.

### 2.7 Шифрование свойств
Клиентское AES-GCM с случайным nonce корректно по конфиденциальности, но:
- нет AAD, привязанного к PK/имени колонки → возможна перестановка
  шифротекстов между строками/колонками (confused-deputy);
- нет версии ключа в формате шифротекста → ротация ключей невозможна;
- нет указания формата (nonce||tag||ct) в контракте `IPropertyValueEncryptor`.

### 2.8 DI и времена жизни
README сам показывает обход: scoped-интерсепторы приходится регистрировать
руками мимо `UseEfInterceptors`. Это архитектурный шов — API имеет два
несовместимых пути. Стоит сделать `UseEfInterceptorsFrom(sp)` полноценным
и поддержать scoped-фабрики внутри `EfInterceptorsSetup`.

### 2.9 Мультитенантность
`MultiTenancySaveChangesInterceptor` защищает только запись; чтения
защищаются отдельным `ApplyTenantFilters`. Забыть второе легко → утечка
данных между тенантами. Плюс: query filter, зависящий от **изменяемого**
`ITenantProvider`, попадает в кэш модели — нужен `IModelCacheKeyFactory`,
учитывающий тенант, иначе первый тенант «зафиксирует» фильтр.
Это самый опасный пункт аудита.

### 2.10 Outbox
Атомарная вставка — верно. Но воркер (`AddOutboxProcessor`) с поллингом
без `FOR UPDATE SKIP LOCKED` / claim-колонки даст двойную доставку при
нескольких инстансах. Нужны: `LockedUntilUtc`, `AttemptCount`,
dead-letter и идемпотентность на стороне хендлера.

## 3. Тестируемость и качество

- 70 тестов на ~60 интерсепторов — примерно 1 тест на компонент. Мало для
  «production-ready»: нет тестов на конкурентность, на порядок, на откат.
- Бенчмарки есть — хорошо; стоит публиковать цифры в README.
- Нет `Directory.Packages.props`/central package management (проверить).
- Нет анализа публичного API (`PublicAPI.Shipped.txt` / ApiCompat) — при
  таком размере поверхности неизбежны ломающие изменения.
